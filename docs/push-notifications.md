# Пуш-уведомления: контракт с приложением

Документ для того, кто пишет приложение. Описывает только пуши; общий контракт приложения с
бэкендом — в отдельной спецификации. Всё, что здесь названо, на бэкенде уже есть и работает.

Транспорт — RuStore (`ru.rustore.sdk:universalpush`). Эндпойнты живут под префиксом `<origin>/user`,
там же, где вход и список устройств: подписка на пуши принадлежит **входу**, а не абстрактному
пользователю.

## 1. Что изменилось против первоначального плана

Если у вас в задаче записаны прежние договорённости, поправьте три вещи:

| Было в плане | Стало |
|---|---|
| `PUT <origin>/control/manage/push/devices` | `PUT <origin>/user/push/subscriptions` — префикс `/user`, а не `/control` |
| `sessionId` в теле регистрации | **не передаётся вовсе** — сервер берёт сессию из access-токена |
| `DELETE …?provider=&token=` | `DELETE <origin>/user/push/subscriptions` с телом `{"token": "…"}` |

Токен доступа теперь несёт claim `asid` — идентификатор сессии входа. Ничего делать с ним не надо,
он нужен серверу; но именно из-за него **после каждого входа подписку надо регистрировать заново**
(см. §5).

## 2. Регистрация подписки

```http
PUT <origin>/user/push/subscriptions
Authorization: Bearer <access-token>
Content-Type: application/json

{ "provider": "rustore", "token": "<токен от SDK>" }
```

```json
{ "response": "ok" }
```

- **Идемпотентно.** Повторный вызов с тем же токеном не создаёт вторую подписку.
- `provider` — как его называет SDK: `rustore`, `firebase`, `hms`. Регистр не важен. Сегодня сервер
  умеет отправлять только через RuStore; токены FCM и HMS он сохранит, но отправлять по ним не
  будет, пока не появятся креды. Незнакомое значение — `400`.
- `token` — до 4096 символов, пустой — `400`.
- `401` — истёкший или неверный access-токен, обычная ваша логика обновления.

## 3. Снятие подписки

```http
DELETE <origin>/user/push/subscriptions
Authorization: Bearer <access-token>
Content-Type: application/json

{ "token": "<токен от SDK>" }
```

Токен едет в теле, а не в query, намеренно: query оседает в логах прокси, а токен — это право слать
на устройство.

Зовите **при выходе из аккаунта, до очистки токенов доступа** — иначе снимать подписку будет нечем.
Идемпотентно: `200` и когда снимать было нечего, повторный выход не должен спотыкаться.

## 4. Когда звать регистрацию

- при каждом успешном входе;
- когда SDK выдал новый токен (ротация, переустановка, очистка данных);
- при старте приложения, если давно не подтверждали — сервер сметает подписки, не появлявшиеся
  **60 дней**.

Повторов сервер не боится: это upsert. Приложение всё же сводит все три повода к одной сверке
(`core/push/PushSubscriptions.kt`): поводы — это состояние «какой вход и какие токены у транспорта»,
а не три независимые отправки. Пока их было три, вход и колбэк SDK о новом токене отправляли один и
тот же токен дважды: `getTokens()` у SDK сам поднимает этот колбэк.

## 5. Жизненный цикл — что происходит без вашего участия

| Событие | Что делает сервер |
|---|---|
| выход из аккаунта | вы зовёте `DELETE`; подписка удаляется |
| **отзыв устройства** в списке «мои устройства» | подписка удаляется вместе с сессией — уведомления прекращаются сразу |
| вход под другим аккаунтом на том же телефоне | тот же токен **переезжает** к новому владельцу, старый владелец уведомлений на этот телефон больше не получает |
| приложение снесли или переустановили | транспорт отвечает «токен не зарегистрирован», подписка удаляется |
| 60 дней без регистрации | подписка сметается |

Практическое следствие: **подписка привязана к входу**. Разлогинились и вошли снова — старая
подписка уже удалена, надо зарегистрировать токен заново. Если этого не сделать, пуши просто
перестанут приходить, и никакой ошибки видно не будет.

### Как приложение проверяет само себя

Молчание — единственный симптом сломанной подписки, поэтому проверка нужна явная. Материал для неё
даёт список входов: у каждой строки `GET /user/sessions/` есть блок `push` — подписки **этого**
входа.

```json
"push": [ { "provider": "RUSTORE", "maskedToken": "cV8kQz1p…",
            "lastSeenAt": "2026-08-19T08:41:03.554120" } ]
```

По своей строке (её приложение узнаёт по `sessionId`, сохранённому вместе с токенами) — два шага:

1. `push` непустой — иначе сервер не знает, куда слать;
2. `maskedToken` хотя бы одной записи совпадает с первыми 8 символами токена, который сейчас держит
   SDK, — иначе на сервере лежит устаревший токен.

Оба «нет» лечатся одинаково: `PUT /user/push/subscriptions` с живым токеном. Вызов идемпотентный,
звать лишний раз безопасно.

**Две-три записи в `push` — норма**, а не поломка: когда транспорт выдаёт новый токен, прежняя
запись живёт до ответа транспорта «такого токена нет» или до планового смёта, и до тех пор
уведомления уходят на обе. Своего эндпойнта для чистки нет, и она не нужна.

`maskedToken` — не токен, а его начало: целиком токен не отдаётся никому, включая владельца.
Сверять префикс можно, отправлять обратно в API — некуда. Человеку показывается один признак
«уведомления приходят», а не список токенов; сами записи — максимум для поддержки.

## 6. Что приходит в пуше

Только `data`, без `notification`-блока — уведомление рисует приложение, поэтому оно может и
промолчать.

| Поле | Всегда | Значение |
|---|---|---|
| `type` | да | `webchat_message` — то же имя, что у события живой доставки |
| `sessionId` | да | переписка; тап открывает именно её |
| `agentId` | да | агент, чтобы открыть чат до загрузки списка сессий |
| `agentName` | да | заголовок уведомления |
| `messageId` | да | ключ дедупликации |
| `preview` | **нет** | первая строка ответа, до 160 символов |

`preview` может отсутствовать: ответ без текста (только вложения) или превью выключено на
инсталляции. Уведомление без превью показывать всё равно надо — «Секретарь: новое сообщение».

Незнакомые поля игнорируйте, их может стать больше.

Пример:

```json
{
  "type": "webchat_message",
  "sessionId": "01991f3e-...",
  "agentId": "0198b2a1-...",
  "agentName": "Секретарь",
  "messageId": "run-8f21-answer",
  "preview": "Отчёт собран, нашёл три расхождения по остаткам"
}
```

## 7. Что делает клиент, а сервер — нет

- **Молчит, когда открыта та же переписка.** Серверу недоступно знание, какой чат сейчас на экране,
  и presence этого не заменяет. Приложение сравнивает `sessionId` с открытым и подавляет показ.
- **Дедуплицирует по `messageId`.** Доставка at-least-once: одно и то же уведомление может прийти
  дважды (повтор доставки на бэкенде, реплей). Второе не должно давать вторую строку в шторке.
- **Схлопывает уведомления переписки.** Collapse-ключа сервер пока не шлёт (в API транспорта поле не
  подтверждено), поэтому за это отвечает клиент: одинаковый notification id на `sessionId`, чтобы
  после суток вне сети в шторке не оказалось десяти уведомлений одного разговора.
- **Спрашивает разрешение** на уведомления (Android 13+). Отказ — нормальный исход, сервер о нём не
  узнает и продолжит отправлять.
- **Не ждёт, что пуш заменит живую доставку.** При открытом приложении придут оба — и событие по
  WebSocket, и пуш; это ожидаемо.

## 8. Границы и края

- Уведомляют **только ответы агента в вебчате**. Промежуточные шаги (`progress`) — а их бывает
  десяток на один ответ — не уведомляют. Своё же отправленное сообщение эхом не вернётся.
- **TTL — час.** Ответ, доставленный к вечеру, не нужен никому: транспорт перестаёт пытаться.
- **Размер сообщения — 4 КБ**, превью обрезано на сервере, вписаться в лимит ваша забота не должна.
- Доставку сервер **не подтверждает**: ответ на регистрацию говорит только о том, что подписка
  записана. Счётчика непрочитанного в payload нет — бейдж считайте сами, из листингов.
- Пуш приходит одновременно на все устройства пользователя; какое из них покажет уведомление, сервер
  не выбирает.

## 9. Чек-лист

- [x] `PUT <origin>/user/push/subscriptions` при входе, при новом токене от SDK и на старте приложения
- [x] `DELETE <origin>/user/push/subscriptions` при выходе — **до** очистки токенов доступа (порядок
      держит `SessionManager.signOut()`, а не экран)
- [x] `sessionId` из тела регистрации убран
- [x] уведомление подавляется, когда открыта эта же переписка
- [x] дедупликация по `messageId`, схлопывание по `sessionId`
- [x] уведомление без `preview` показывается корректно
- [x] тап открывает переписку `sessionId` (агент — `agentId`, заголовок — `agentName`)
- [x] признак «уведомления работают» считается по `push` своей строки и совпадению префикса токена
- [x] расхождение префикса или пустой `push` лечится перерегистрацией, несколько записей — не ошибка

## 10. Где это в приложении

Раздел добавлен на стороне приложения — чтобы по контракту было видно, куда смотреть.

| Что | Где |
|---|---|
| подъём транспорта, токены, слушатели | `core/push/PushClient.kt` (интерфейс — `PushTransport.kt`) |
| регистрация и снятие подписки — единственный отправитель | `core/push/PushSubscriptions.kt` |
| что подтверждено серверу и правило сверки | `core/push/PushRegistrationLog.kt` (`pushDue`) |
| какой сейчас вход — один источник на приложение | `core/auth/CurrentSession.kt` |
| подъём транспорта и показ пришедшего | `core/push/PushSync.kt` |
| разбор payload и правило «показывать или нет» | `core/push/PushMessage.kt` |
| дедупликация по `messageId` | `core/push/PushDedup.kt` |
| канал, построение уведомления, адрес тапа | `core/push/PushNotifier.kt` |
| приложение на экране или свёрнуто | `core/push/AppVisibility.kt` |
| запрос разрешения (Android 13+) | `core/push/PushPermission.kt` |
| проверка «уведомления работают» и её лечение | `core/push/PushHealth.kt`, `PushSubscriptions.health()` / `.repair()` |
| экран «мои устройства» | `feature/profile/ProfileScreen.kt` |
| эндпойнты | `data/push/PushApi.kt`, блок `push` — в `data/user/UserApi.kt` |

`RUSTORE_PROJECT_ID` задаётся `buildConfigField` отдельно для `dev` и `prod`: в консоли RuStore у
проекта push один отпечаток подписи, а отладочная и релизная подписи разные. Пустой идентификатор —
транспорт не поднимается, приложение работает как раньше.
