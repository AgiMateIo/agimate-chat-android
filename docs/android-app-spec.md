# Нативное Android-приложение: спецификация

Документ для того, кто пишет приложение. Он описывает контракт с бэкендом и обязанности клиента;
визуальные макеты приходят отдельно. Всё, что здесь названо, на бэкенде уже существует и работает —
это не план, а описание готовой поверхности.

Главное отличие от веб-клиента — **авторизация**. Веб держит refresh-токен в httpOnly-cookie;
приложению так нельзя, и для него сделан отдельный обмен. Раздел 3 — самый важный в документе.

## 1. Продукт в двух абзацах

AgiMate — платформа, где человек заводит собственных ИИ-агентов: у агента есть роль, инструкция,
память, он работает по расписанию и ходит в подключённые сервисы. Это приложение — **мессенджер с
моими агентами**: список агентов как список контактов и переписка с ними.

Аудитория — не разработчики: частные пользователи и малый бизнес, люди, умеющие пользоваться
Telegram. Язык интерфейса русский. Главная метафора: **агент — это контакт**. Всё сложное
(интеграции, навыки, политики доступа, выбор моделей, биллинг, доски задач, таблицы) живёт в
отдельном админском интерфейсе и в приложении не появляется вообще.

## 2. Адреса и общая форма API

Два сервиса за одним хостом:

| Префикс | Что там |
|---|---|
| `<origin>/user` | вход, токены, сессии устройств, профиль |
| `<origin>/control` | агенты, контакты, переписки, файлы |
| `<origin>/connection/websocket` | WebSocket real-time (адрес приходит с сервера, зашивать не надо) |

Успешный ответ всегда завёрнут: `{"response": <данные>}`. Ошибка — `{"error": {"message": "…"}}`.
Постраничный ответ: `{"content": [...], "number": 0, "size": 50, "totalElements": 120,
"totalPages": 3}`, нумерация с нуля.

Время — локальное без зоны (`2026-08-15T16:44:13.310006`). Зоны в API нет нигде; трактовать как
время сервера.

**Слэш в конце пути — значимый.** `GET /manage/sessions/` и `POST /manage/webchat/sessions` —
разные маршруты, и лишний или недостающий слэш даёт 404. Правило простое: путь, отдающий список,
заканчивается слэшем. Ниже все пути выписаны точно, копируйте как есть.

**Переписка — один ресурс `/manage/sessions`**, чем бы она ни шла: веб-чатом, мессенджером, IDE.
Листинг, история, отметка прочтения и закрытие общие. В `/manage/webchat` остался только транспорт:
начать чат, отправить сообщение, взять токен на живой канал, список контактов.

Авторизация запросов — `Authorization: Bearer <accessToken>` к обоим сервисам, токен один и тот же.

## 3. Авторизация

### 3.1 Почему не как в вебе

Дверей в аккаунт четыре, и три из них приложению нужны: провайдер через браузер (§3.2), пароль
(§3.5) и письмо, заводящее пароль (§3.6). Четвёртая — привязка ещё одного провайдера к уже открытому
аккаунту (§3.7); токенов она не выдаёт.

Провайдерский путь идёт через внешний браузер (Custom Tabs), а у него свой cookie jar, до которого
HTTP-клиент приложения не дотягивается. Поэтому вход заканчивается не установкой cookie, а **одноразовым кодом**
в редиректе, который приложение меняет на пару токенов в теле ответа. Это authorization code flow с
PKCE, только сервер авторизации — наш же бэкенд.

**Встроенный WebView использовать нельзя.** Google отклоняет в нём OAuth (`disallowed_useragent`),
то есть путь ломается на первом же провайдере из четырёх. Только Custom Tabs.

### 3.2 Флоу целиком

**Шаг 1. Открыть вход в Custom Tabs.**

```
GET <origin>/user/oauth2/authorization/{provider}
      ?redirect_to=<адрес возврата>
      &code_challenge=<S256-challenge>
      &ref=<реферальный код>          ← необязательно, только если человек пришёл по ссылке
```

`provider` — `google`, `yandex`, `vk` или `github`. Набор кнопок на экране входа определяется тем,
какие провайдеры включены в инсталляции; ошибочный провайдер — ошибка входа, а не пустой экран.

**Шаг 2. Круг к провайдеру.** Ничего делать не нужно, всё происходит в браузере.

**Шаг 3. Возврат.** Бэкенд редиректит на `redirect_to` с кодом:

```
<redirect_to>?code=<одноразовый код>
```

Ни одной cookie в этом ответе нет и быть не должно. Если что-то пошло не так, вместо `code` придёт
`?error=invalid_request` — приложение обязано это обработать и показать «войти ещё раз», а не
зависнуть в ожидании.

**Шаг 4. Обмен кода на токены.**

```
POST <origin>/user/oauth2/native/token
Content-Type: application/json

{ "code": "…", "codeVerifier": "…", "redirectUri": "agimate://auth", "deviceName": "Pixel 8" }
```

```json
{ "response": {
    "accessToken": "eyJhbGciOiJFUzI1NiJ9…",
    "refreshTokenId": "6ba82a93-a7e7-4266-90a6-4d9695f97acb",
    "refreshToken": "eyJhbGciOiJFUzI1NiJ9…",
    "expiresIn": 3600,
    "sessionId": "01a00699-8e6e-752e-a6b3-62e110f6f237" } }
```

- `redirectUri` — **тот же** адрес, что был в `redirect_to`; несовпадение даёт 403. Это часть
  привязки кода, а не формальность;
- `deviceName` — как устройство будет называться в списке «мои устройства». Необязателен, но без
  него в списке окажется строка User-Agent, что человеку ни о чём не говорит;
- `sessionId` — строка этого устройства в списке сессий. Сохранить: по нему приложение узнаёт себя
  в списке устройств;
- код живёт **60 секунд** и гасится первым обменом. Второй обмен тем же кодом не просто отказ — он
  **отзывает сессию**, которую выдал первый. Не повторять запрос вслепую при сетевой ошибке: если
  ответ не дошёл, безопаснее начать вход заново.

### 3.3 PKCE: точные требования

- `code_verifier` — случайная строка **43–128 символов** из алфавита `A–Z a–z 0–9 - . _ ~`.
  Практически: 32 случайных байта → base64url без паддинга даёт ровно 43 символа;
- `code_challenge` = base64url-без-паддинга( SHA-256( ASCII(code_verifier) ) ) — **ровно 43
  символа**;
- метод — **только S256**. Параметр `code_challenge_method` сервер не читает; `plain` не
  поддерживается;
- challenge неверной длины или с символами вне base64url молча игнорируется, и вход закончится
  `?error=invalid_request`;
- verifier хранить в памяти процесса на время входа. Он живёт минуты и не должен переживать вход.

### 3.4 App Link против схемы

Адрес возврата бывает двух видов, и оба должны быть заранее разрешены на сервере — произвольный
адрес не примут.

**Предпочтительно — App Link:** `https://<домен>/app/auth`. Он проверяется доменом, и присвоить его
чужому приложению нельзя. Для этого на домене должен лежать `/.well-known/assetlinks.json` с
отпечатком подписи приложения. Это работа со стороны инфраструктуры, но инициировать её и дать
отпечаток — задача разработчика приложения. **Отпечаток меняется при переходе на подпись Google
Play**: файл придётся обновить, иначе ссылка молча перестанет открывать приложение.

**Фолбэк — схема:** `agimate://auth`. Схему может зарегистрировать на себя чужое приложение, и
именно поэтому PKCE обязателен: перехваченный код без verifier'а бесполезен.

**Проверка домена может не сработать** — пользователь отключил открытие в приложении, верификация не
прошла. Тогда редирект уйдёт в браузер и приложение кода не увидит. Оно обязано это пережить: экран
входа с возможностью повторить, а не бесконечный спиннер.

### 3.5 Вход по паролю

```
POST <origin>/user/auth/login
Content-Type: application/json

{ "email": "…", "password": "…", "client": "NATIVE", "deviceName": "Pixel 8" }
```

Ответ — та же пара токенов, что у обмена кода.

- **`client: "NATIVE"` обязан уехать в теле явно.** Без него сервер читает запрос как веб: кладёт
  refresh в cookie, а в теле оставляет `null`. Cookie у приложения нет, и вход кончается половиной
  пары. Сериализатор, настроенный на `encodeDefaults = false`, поле со значением по умолчанию не
  пишет — это единственное место контракта, где настройка JSON решает, войдёт человек или нет;
- `401` — неизвестный адрес и неверный пароль **одинаково**, и одинаково по времени ответа.
  Различать их на экране нечем и не надо: разный текст на два случая и был бы проверялкой, кто
  здесь зарегистрирован;
- `429` — десять неудач по одному ящику за 15 минут. Срок повтора сервер называет в тексте,
  показывать его как есть.

**Требования к паролю: от 8 символов, не больше 72 байт.** Граница в байтах, а не в символах,
потому что алгоритм хеша читает 72 байта и об остальном молчит: сорок кириллических букв уже за
границей, а по символам выглядят коротким паролем. Форма обязана считать байты UTF-8, иначе
пропустит то, что сервер отвергнет. Требований к составу (цифра, заглавная, спецсимвол) нет
намеренно, и придумывать их на клиенте нельзя.

### 3.6 Регистрация и пароль по письму

```
POST /user/auth/register          { email, displayName?, ref? }   → 200 всегда
POST /user/auth/register/resend   { email }                       → 200 всегда
POST /user/auth/password/forgot   { email }                       → 200 всегда
```

**Пароля в заявке нет, и это не упущение.** Его называет тот, кто откроет письмо. Иначе пароль
называет один человек, а ящик доказывает другой.

**Ответ одинаков всегда** — адрес свободен, занят или ему уже слали пять писем за час. Экран должен
говорить «если адрес можно зарегистрировать, письмо отправлено», а не «письмо отправлено»: второе
было бы обещанием, которого сервер не давал.

**Ссылка из письма ведёт на веб** (`{фронт}/register/confirm?token=…`,
`{фронт}/password/reset?token=…`), и приложение её не ловит: App Link выключен, а домен фронта —
не домен API. Поэтому путь в приложении такой: заявка → «проверьте почту» → пароль назначается в
браузере → человек возвращается и входит формой из §3.5. Эндпойнты `register/confirm` и
`password/reset` приложению не нужны вовсе — токена из письма у него нет.

**`503` — почта на установке не настроена.** Так отвечают все три запроса выше; вход и подтверждение
уже полученной ссылки работают. Узнать заранее нечем — отдельного «а есть ли здесь почта» у сервера
нет, — поэтому признак берётся из первого же отказа, и после него прячутся обе двери: и
регистрация, и «забыли пароль».

### 3.7 Привязка провайдера

Добавляет ещё одну дверь к аккаунту, в который человек уже вошёл. Единственный способ привязать
провайдера, чей ящик **другой**: обычный вход связывает по подтверждённому адресу и такой случай
решить не может.

```
GET  <origin>/user/oauth2/authorization/{provider}?link=1&redirect_to=<адрес возврата>
        → провайдер → {redirect_to}?link_proof=<64 hex>&provider=github
POST <origin>/user/auth/methods/link   { "proof": "3f2a…c81" }   (Bearer)
        → { "provider": "GITHUB", "outcome": "LINKED" }
```

- `link=1` — ровно эта строка, иначе круг читается как обычный вход и заводит второй аккаунт вместо
  второй двери в этот;
- PKCE здесь нет и не нужен: круг не выдаёт ни кода, ни токенов;
- **возврат приходит в тот же deep link, что и вход**, и различать их приходится по параметру:
  `code` — это вход, `link_proof` — это привязка;
- доказательство живёт **5 минут** и тратится один раз. Пять минут — это на дорогу от колбэка до
  запроса, а не на раздумья: гасить сразу по возвращении, не дожидаясь действий человека.

**Почему два шага.** Круг к провайдеру начинается с перехода по адресу, а заставить браузер перейти
по адресу может чужая страница. Если бы привязку совершал колбэк, ею распоряжался бы тот, кто круг
вызвал. Поэтому круг устанавливает только провайдера, а аккаунт называет второй запрос — заголовком
`Authorization`, который чужая страница послать не может. Отсюда же следует, что `link_proof` сам по
себе не опасен: без токена владельца он не обменивается ни на что.

| `outcome` | Что показать |
|---|---|
| `LINKED` | Готово, перечитать список способов входа |
| `ALREADY_YOURS` | Уже был привязан — не ошибка, тот же экран успеха |
| `TAKEN` | «Этот аккаунт {провайдера} уже привязан к другому пользователю» |
| `PROVIDER_OCCUPIED` | «У вас уже привязан другой аккаунт {провайдера}, отвяжите его сначала» |

**Все четыре приходят с кодом 200.** Два последних — отказы по существу, но с самим запросом всё в
порядке; различать их надо по `outcome`, а не по статусу. Отдельно **403** — доказательство
просрочено, потрачено или подделано: предложить пройти круг заново. Исход, которого клиент не знает,
показывать как отказ, а не как успех.

### 3.8 Способы входа

```
GET    <origin>/user/auth/methods/                 → список     (слэш значим)
POST   <origin>/user/auth/methods/link             → привязать  (§3.7)
DELETE <origin>/user/auth/methods/oauth/{PROVIDER} → отвязать   (ЗАГЛАВНЫМИ)
DELETE <origin>/user/auth/methods/password         → убрать пароль
POST   <origin>/user/auth/password/change          { currentPassword, newPassword }
```

**Регистр провайдера в путях разный, и это не опечатка.** В круг к провайдеру он едет строчными
(`github` — идентификатор регистрации у самого провайдера), в отвязку — заглавными (`GITHUB` —
значение перечисления).

- одна запись на способ: провайдеры от старых к новым, пароль последним. У записи провайдера `email`
  бывает `null` — привязанный вручную провайдер вправе адреса не сообщать;
- **последний способ входа не отвязывается**: оба `DELETE` отвечают 400, если взамен ничего не
  остаётся. Кнопку в таком состоянии гасить заранее, а не ловить отказ;
- «добавить пароль» — это `password/forgot` из §3.6: одна операция, две точки входа. Пароль
  задаётся по ссылке из письма, а не формой в приложении: аккаунт без пароля тем и отличается, что
  подтвердить право на него нечем, кроме ящика;
- смена пароля гасит все **остальные** сессии, текущая переживает. Сброс по письму гасит **все**,
  включая ту, из которой его запросили;
- экран открыт и аккаунту в ожидании одобрения (роль `GUEST`) — как и список устройств;
- о каждом изменении владельцу уходит письмо. Это ожидаемое поведение, и в интерфейсе про него
  стоит предупредить;
- время в этом листинге приходит через пробел (`2026-08-15 21:05:21`), а не по ISO, как в остальных.

### 3.9 Обновление токенов

Access живёт **час**, refresh — **60 дней**, и при каждом обновлении оба меняются (ротация). Срок
сессии сдвигается вперёд при каждом обновлении: сессия умирает от простоя, а не от возраста.

**Срок брать из `expiresIn` ответа, а не из константы в коде**: сервер меняет его без предупреждения
клиентов — вебу он в августе 2026 уехал с суток на час. Приложения это не коснулось, но константа,
переписанная руками однажды, второй раз переписана не будет.

**Обе половины политики сразу**: обновляться заранее, примерно на девяти десятых срока, **и**
обрабатывать 401 повторным обновлением с одним ретраем. Одного 401-круга мало: часовой токен успевает
протухнуть, пока телефон спит, и первый же запрос после пробуждения платил бы за это лишним кругом.
Планировщика для этого не нужно — достаточно проверять срок при возвращении в приложение.

```
POST <origin>/user/oauth2/refresh
Content-Type: application/json

{ "refreshToken": "…" }
```

Ответ — та же форма, что у обмена кода. **Новую пару сохранять атомарно**, до следующего сетевого
запроса.

**Обновление обязано быть однопоточным.** На холодном старте приложение легко выпускает пять
параллельных запросов, все получают 401 и все идут обновляться. Ротация — условная запись: поколение
сдвинет ровно один, остальные получат `409`. Оберните обновление мьютексом (single-flight): один
запрос обновляется, остальные ждут его результата и повторяются с новым токеном.

Коды ответа и что делать:

| Код | Значение | Действие клиента |
|---|---|---|
| `200` | новая пара | сохранить, повторить исходный запрос |
| `409` | параллельное обновление, победил другой | подождать свой single-flight и повторить с актуальным токеном; **не разлогинивать** |
| `403` | токен недействителен, сессия отозвана или истекла | стереть токены, показать экран входа |
| `401` | токена в запросе не было | ошибка клиента: обновляться нечем, вести на вход |

**403 — это всегда «вход заново».** Причины разные (сессию отозвали с другого устройства, токен
предъявлен после ротации, сессия истекла), но действие одно, и различать их в UI не нужно.

**Про потерянный ответ.** Сервер знает, что мобильная сеть теряет ответы: обновление, ответ на
которое не доехал, можно повторить тем же старым токеном в течение **минуты** после ротации — вернётся
актуальная пара. Это страховка на стороне сервера, а не разрешение обновляться как попало: за
пределами минуты тот же токен читается как кража и гасит всю сессию. Практический вывод — при
сетевой ошибке во время обновления повторять **тем же** токеном (а не начинать вход заново), и
только в пределах минуты.

### 3.10 Хранение токенов

- refresh-токен и access-токен — в `EncryptedSharedPreferences` (ключ в Android Keystore). Обычные
  `SharedPreferences` не годятся: refresh живёт два месяца;
- **исключить из авто-бэкапа**: `android:allowBackup="false"` либо явные правила исключения.
  Иначе токен уезжает в облако и приезжает на другое устройство;
- `sessionId` можно хранить рядом, он не секрет;
- момент, с которого пора обновляться заранее, — тоже рядом: он выводится из `expiresIn` один раз,
  при сохранении пары, и не пересчитывается каждым, кто заглянул в хранилище;
- при 403 на обновлении — стирать всё разом.

### 3.11 Логаут и список устройств

```
POST <origin>/user/oauth2/logout
{ "refreshToken": "…" }
```

Логаут отзывает строку сессии на сервере — токен перестаёт работать везде, а не только на этом
устройстве. Локальную очистку делать всё равно.

```
GET    <origin>/user/sessions/          → список активных сессий
DELETE <origin>/user/sessions/{id}      → отозвать одну
```

```json
{ "response": [
    { "id": "01a00699-8e6e-752e-a6b3-62e110f6f237",
      "client": "NATIVE",
      "deviceLabel": "Pixel 8",
      "createdAt": "2026-08-15T21:05:21.903002",
      "lastSeenAt": "2026-08-19T08:41:02.117441",
      "push": [
        { "provider": "RUSTORE",
          "maskedToken": "cV8kQz1p…",
          "lastSeenAt": "2026-08-19T08:41:03.554120" } ] } ] }
```

`client` — `NATIVE` или `WEB`; браузерные входы видны в том же списке. Своё устройство узнаётся по
`sessionId`, сохранённому при обмене кода, — помечать его «это устройство» и не давать отозвать
случайно. Отдельной операции «выйти на остальных» нет: перебрать список и позвать `DELETE` на
каждое чужое. Отозванные и истёкшие входы не приходят вовсе: всё, что в списке, — живое, свежие
сверху (сортировка по `lastSeenAt`).

Экран открыт и аккаунту в ожидании одобрения (`GUEST`): потерявшему телефон отзыв нужен раньше,
чем одобрение.

**`push` — подписки этого входа на уведомления** (см. `docs/push-notifications.md`). Пустой список
значит, что уведомления на устройство не идут. Две-три записи — норма: когда транспорт выдаёт новый
токен, прежняя живёт до его отказа или планового смёта. Чистить их нечем и незачем.

Признак «уведомления на этом устройстве работают» считается по своей строке в два шага: `push`
непустой **и** `maskedToken` хотя бы одной записи совпадает с началом токена, который сейчас держит
SDK. Оба «нет» лечатся одинаково — `PUT /user/push/subscriptions`, вызов идемпотентный. `maskedToken`
— первые 8 символов и многоточие: целиком токен не отдаётся никому, включая владельца, так что
сверять можно только префикс, а отправлять обратно в API его некуда.

Ответы `DELETE`:

| Ответ | Когда | Что делать |
|---|---|---|
| `200` | Отозвано | Перечитать список |
| `404` | Входа нет или он чужой | Перечитать список |
| `401` | Access протух | Обновить токены и повторить |
| `403` | Отозвана уже **своя** сессия | Локальный выход: чистить токены и вести на вход |

**Отзыв бьёт по refresh, а не по каждому запросу.** У отозванного устройства перестаёт работать
обновление, а уже выданный access доживает свой час. Это осознанный размен: сервер не ходит в базу
на каждый запрос. А вот **уведомления прекращаются сразу**: подписка удаляется вместе с входом.
Обещать в UI «отключится мгновенно» всё равно не стоит — час чужого access-токена никуда не денется.

Отзыв **своей** строки через `DELETE` работает и делает на сервере то же, что логаут, но локальное
состояние приложением не чистится. Поэтому выход из аккаунта — прежним путём (§3.11), а своя строка
в списке от отзыва защищена.

### 3.12 Гейт «ждём одобрения»

Новый аккаунт заводится с ролью `GUEST` и до одобрения администратором в продукт не попадает. Это
**не** ошибка авторизации: вход прошёл, токены выданы, а агентов завести нельзя.

```
GET <origin>/user/user/me
```

Да, `user` дважды — так исторически устроен путь профиля, это не опечатка.

```json
{ "response": { "id": "…", "email": "…", "displayName": "…", "role": "GUEST", "createdAt": "…" } }
```

`role` = `GUEST` → показать экран ожидания: чего ждём, сколько примерно, что делать дальше. Он не
должен выглядеть ошибкой. `USER` или `ADMIN` → обычная работа. Проверять при старте и после каждого
возвращения в приложение — одобрение может прийти в любой момент.

## 4. Контакты и переписки

### 4.1 Список контактов — один запрос на экран

```
GET <origin>/control/manage/webchat/contacts/?page=0&size=50
```

Строка: `agentId`, `name`, `description`, `enabled`, `unreadCount`, `lastMessage`, `lastSessionId`,
`lastActivityAt`, `isRunning`.

```json
{ "agentId": "…", "name": "Ассистент", "description": "помощник", "enabled": true,
  "unreadCount": 2,
  "lastMessage": { "text": "готово", "direction": "AGENT", "hasAttachments": false,
                   "createdAt": "2026-08-15T16:43:13.310759" },
  "lastSessionId": "…", "lastActivityAt": "2026-08-15T16:44:13.310006", "isRunning": true }
```

- порядок — по свежести переписки, агенты без чатов в хвосте. **Не пересортировывать на клиенте**:
  ключ сортировки серверный, между страницами такой порядок не восстановить;
- `lastSessionId` — переписка, из которой взято превью; по тапу открывать именно её. `null` у
  агента, которому ещё не писали;
- `lastMessage.text` обрезан до 160 символов сервером и может быть `null` при
  `hasAttachments: true` — рисовать «Вложение», а не пустую строку;
- `enabled: false` — агент выключен: историю показывать, отправку запрещать;
- **аватарок в API нет и не будет.** Генерировать на клиенте детерминированно из имени.

### 4.2 Переписки одного агента

```
GET <origin>/control/manage/sessions/?agentId=<agentId>&connectorCode=webchat&page=0&size=50
```

Строка: `id`, `channelId`, `agentId`, `connectorCode`, `title` (генерируется из первого сообщения),
`lastActivityAt`, `closedAt`, `createdAt`, `unreadCount`, `lastMessage`, `isRunning`.

**`connectorCode` в запросе обязателен, хотя формально фильтр необязательный.** Без него ресурс
отдаёт все переписки пользователя: сессии в мессенджерах и поток событий подключения вовсе без
канала (`channelId` = `null`). У такой строки `unreadCount`, `lastMessage` и `isRunning` приходят
нулями — непрочитанное во внешнем мессенджере ведёт он сам, и бейдж по ней рисовать нельзя.

Закрытые переписки приходят вместе с открытыми, фильтра нет — различать по `closedAt`. Историю они
хранят, но отправку в них сервер запрещает (400).

```
GET    <origin>/control/manage/sessions/{id}                                ← одна переписка
PATCH  <origin>/control/manage/sessions/{id}          { "title": "…" }      ← переименовать
POST   <origin>/control/manage/sessions/{id}/close                          ← закрыть
POST   <origin>/control/manage/webchat/sessions       { "agentId": "…" }    ← начать, без слэша
```

Строку одного и того же вида отдают все пять ответов — листинг, `GET` по id, переименование,
закрытие и старт, — и приходит она уже обогащённой бейджем и `isRunning`: ответ можно класть обратно
в список как есть.

Новую переписку можно создавать в любой момент; закрытие гасит бейдж — сессия помечается прочитанной
целиком. Заголовок при переименовании — до 80 символов, длиннее — `400`, а не молчаливая обрезка;
вернуть автоматический заголовок нечем, переименование перекрывает его насовсем.

### 4.3 История сообщений

```
GET <origin>/control/manage/sessions/{id}/messages/?page=0&size=50
```

**Порядок — от новых к старым.** Первая страница — конец переписки; листание вверх — это `page+1`.

```json
{ "id": "10000000-0000-7000-8000-000000000005",
  "messageId": "run-42-answer",
  "direction": "AGENT",
  "stream": "answer",
  "text": "Готово, вот отчёт",
  "parts": [ { "type": "image", "fileId": "agf_…", "mime": "image/png", "size": 384211,
               "name": null, "url": "/files/agf_…?exp=…&sig=…" } ],
  "createdAt": "2026-08-15T16:43:13.310759" }
```

Два идентификатора, и они не взаимозаменяемы:

- `id` — идентификатор строки, по нему считается порядок и им отмечают прочтение;
- `messageId` — ключ доставки, по нему дедуплицируются real-time события. Порядка не несёт.

Форма истории одна на все каналы, поэтому `messageId` и `parts` вне веб-чата приходят `null`: у
переписки во внешнем мессенджере доставочного id и вложений в этом виде просто нет. Это поля
веб-чата — общий код на них не завязывать, дедупликация вне веб-чата идёт по `id`.

`stream` у сообщений агента: `answer`, `progress` или `error`; у своих сообщений — `null`.

### 4.4 Отправка

```
POST <origin>/control/manage/webchat/sessions/{id}/messages
{ "text": "посчитай расходы", "parts": [ { "fileId": "agf_…" } ] }
```

`text` и `parts` по отдельности необязательны, но пустым не может быть всё сразу (400). Максимум
**5 вложений**. Ответ — `{"sessionId": "…", "messageId": "…"}`.

Отправка **синхронная**: маршрутизация происходит внутри запроса, поэтому ошибка приходит сразу, а
не «принято, а потом упало».

**Поле ввода не блокируется, пока агент отвечает.** Сообщение, отправленное во время ответа,
подхватывается тем же ответом — это штатный сценарий, а не гонка. Показать это состояние так, чтобы
человек не решил, что сообщение потерялось.

### 4.5 Вложения

Файл — сущность control-api, а не вложение переписки. Идентификатор `agf_…` и есть валюта: клиент
загружает байты один раз и дальше передаёт только его. Граница доступа — **пользователь**, а не
агент или разговор; `agentId`/`origin`/`sessionId` — это провенанс и навигация, а не права.

Отправка двухшаговая:

```
POST <origin>/control/manage/files
Content-Type: multipart/form-data;  части — file и origin
```

→ то же представление файла, что в листинге: `{"id": "agf_…", "name": "чек.png", "type": "image",
"mime": "image/png", "size": 384211, "createdAt": "…", "expiresAt": "…", "url": "/files/agf_…?…"}`.
Затем `id` кладётся в `parts` при отправке — **ключ там называется `fileId`**, и совпадать эти два
имени не обязаны.

Своего эндпойнта загрузки у вебчата больше нет: `POST /manage/webchat/files` удалён.

`origin` — метка места в интерфейсе, откуда файл пришёл; сохранится как `user:<метка>` и вернётся в
листинге. Алфавит узкий (`[a-z0-9][a-z0-9_-]{0,31}`), иначе 400: колонка общая с серверным
провенансом (`telegram:<id>`), и префикс — то, что не даёт загрузке представиться коннектором.

**Загрузка ничего ни к чему не привязывает.** Файл лежит в аккаунте, пока его куда-нибудь не
приложат: загрузка предшествует отправке, и получателя на этот момент ещё нет.

Ограничения: **50 МБ** на файл, **500 МБ в сутки** на пользователя (оба — 400 с числами в
сообщении), **30 загрузок в минуту** (429; заголовка `Retry-After` нет, паузу подобрать самому).

**Сроки разные.** Загруженное человеком живёт **90 дней**, произведённое коннектором — скриншот,
сгенерированная картинка, экспорт таблицы — **7**. `agf_` из старой истории может не открыться, и
это штатное состояние, а не ошибка.

**Ссылки на содержимое подписаны и живут 15 минут.** Поле `url` приходит **в двух видах**, и оба
могут оказаться в одном ответе вперемешку:

- относительный путь **без префикса `/control`** — полный адрес собирается как `<origin>` +
  `/control` + `url`;
- абсолютный URL прямо в объектное хранилище (`https://s3.cloud.ru/…?X-Amz-Signature=…`) — брать
  **как есть**, приклеенный origin даёт мусор.

Вид выбирает сервер по файлу; клиент на это не влияет и предсказать не может. Относительный путь —
штатный запасной путь (например, у файла не проставлен mime), а не признак сбоя. Подпись в обоих
случаях внутри самого адреса (`exp`+`sig` либо SigV4), заголовки не нужны — адрес отдаётся
загрузчику картинок напрямую.

**`403` на содержимом — это протухшая подпись, а не потерянный доступ.** Правильная реакция —
перезапросить выдачу, где ссылка подписывается заново, и только если файла нет и в листинге,
считать его ушедшим по сроку. Ссылку нельзя хранить между сессиями: кэшировать надо байты, а не URL.

Перемотка видео и докачка работают **только** на пресайненных ссылках: собственный стриминг сервера
Range-запросов не умеет и отдаёт объект целиком.

Отзыв ссылки слабее, чем кажется: пресайненная не проходит через таблицу файлов и переживает
удаление файла до ближайшей чистки блобов.

### 4.6 Список файлов

```
GET    <origin>/control/manage/files/?sessionId=…&name=…&page=0&size=30
DELETE <origin>/control/manage/files/{fileId}
```

Свои файлы, свежие сверху. Выборка идёт по тем же условиям, что и открытие файла, поэтому список
никогда не предложит того, что откажется скачаться.

- `sessionId` — файлы одного разговора: и присланные человеком, и отданные агентом, и произведённые
  инструментом внутри него. Это готовая панель вложений переписки;
- `agentId` — «связан с агентом»: произвёл файл **или видел** его. В приложении не используется:
  такую границу в интерфейсе не объяснить;
- `name` — подстрока имени, регистронезависимо. Имя есть не у всего (фото из чата, сгенерированная
  картинка приходят без имени), и такие файлы под фильтром по имени не находятся.

Удаление убирает файл раньше срока: из листинга он пропадает сразу, байты живут ещё до минуты.
Дальше `agf_`-ссылки в истории перестают резолвиться ровно так же, как при протухании.

`POST /app/files` и `GET /app/files/{id}` — **не для нас**: это канал подключённых приложений со
своим ключом. Мобильное приложение ходит в `/manage/files` с обычным JWT.

### 4.7 Отметка прочтения

```
POST <origin>/control/manage/sessions/{id}/read
{ "lastReadMessageId": "10000000-0000-7000-8000-000000000005" }
```

Тело необязательно — без него сессия помечается прочитанной до конца. **Передаётся `id` строки, а
не `messageId`** — иначе 400.

Указатель двигается только вперёд: повторный вызов со старым `id` не ошибка, просто ничего не
меняет. Это защита от второго устройства, открывшего старый вид переписки.

Непрочитанным считается сообщение агента со `stream` = `answer` или `error`. `progress` не считается
(один ответ проходит через десяток промежуточных строк, и бейдж показывал бы «12» про одну реплику),
свои сообщения не считаются никогда.

Звать: при открытии чата (без тела) и когда человек долистал до конца, если читал с середины. На
каждое входящее не нужно — бейдж гасится сам при отправке своего сообщения и при закрытии сессии.

## 5. Real-time

Транспорт — Centrifugo поверх WebSocket. **Клиент не может подписаться сам**: и подключение, и
каждая подписка требуют серверного токена.

```
POST <origin>/control/manage/centrifugo/token                      → канал user:{userId}
POST <origin>/control/manage/webchat/sessions/{id}/token           → канал webchat:{sessionId}
```

Оба отдают одинаковую форму: `{"connectionToken": "…", "subscriptionToken": "…", "channel": "…",
"wsUrl": "…"}`. `wsUrl` брать из ответа, не зашивать. **Токены живут час** — обновлять по таймеру и
при реконнекте.

**Два канала с разными ролями.**

`user:{userId}` — одна подписка на всё приложение, живёт всегда. Оттуда приходит тонкое событие,
поднимающее бейджи, пока чат не открыт:

```json
{ "type": "webchat_activity",
  "payload": { "agentId": "…", "sessionId": "…", "messageId": "…", "stream": "answer",
               "preview": "готово", "createdAt": "…" } }
```

Только для `answer` и `error`; для `progress` и для эха своих сообщений — нет. Событие
best-effort: при сбое публикации теряется, и счётчик чинится следующим листингом. Не делать его
единственным источником правды для бейджа.

`webchat:{sessionId}` — подписка на время открытого чата. Оттуда приходят сами сообщения:

```json
{ "type": "webchat_message",
  "payload": { "sessionId": "…", "channelId": "…", "agentId": "…", "messageId": "…",
               "direction": "AGENT", "stream": "answer", "text": "…", "parts": [ … ],
               "createdAt": "…" } }
```

Правила, без которых лента поедет:

- **доставка at-least-once — дедуплицировать по `messageId`.** Одно и то же сообщение может прийти
  дважды;
- своё сообщение возвращается эхом с `direction: "USER"` — это синхронизация между устройствами.
  Оптимистично показанное сообщение схлопнуть с эхом, а не показать дважды;
- у канала включены история и восстановление: после реконнекта Centrifugo досылает пропущенное.
  Перечитывать историю HTTP-запросом после каждого разрыва не нужно;
- если чат открыт, то же сообщение придёт и в `user:{userId}` как `webchat_activity` — использовать
  его только для счётчика и **не растить счётчик для открытой прямо сейчас сессии**.

**Три вида ответа агента.** `progress` — промежуточные шаги («читаю таблицу», «ищу письмо»); их
бывает много подряд, они важны, но не должны засорять ленту пузырями. `answer` — сам ответ, markdown
(списки, жирный, код, ссылки, таблицы). `error` — ошибка вместо ответа. Ответ может занять и три
секунды, и минуту.

## 6. Остановка ответа

```
POST <origin>/control/manage/runs/sessions/{sessionId}/cancel
```

→ `{"sessionId": "…", "cancelled": 2}` — сколько запусков попало под отмену.

**Отменять по сессии, а не по запуску.** Отмена одного запуска позволит стартовать следующему из
очереди этой же сессии; кнопка «стоп» в чате должна останавливать переписку целиком. Операция
идемпотентна, повторное нажатие безопасно.

`isRunning` из листингов — признак «агент сейчас работает», для восстановления состояния при
открытии экрана. Гаснет он приходом `answer` или `error` по real-time, а не опросом. Запуск,
зависший в очереди, перестаёт считаться живым через 15 минут. Известное ограничение: если остановить
ответ с другого устройства, здесь «печатает…» погаснет только при следующем запросе списка.

## 7. Создание агента

Ровно два шага, без интеграций, навыков и выбора моделей **в интерфейсе** — но не в запросах: см.
«Шаг 3» ниже, без него роль остаётся пустой оболочкой.

**Шаг 1 — галерея ролей.**

```
GET <origin>/control/manage/agent-presets/
```

Отдаёт **не постраничный** список: `id`, `name` (слаг вида `personal-assistant`), `title`,
`description`, `instructions` (готовый текст на 1500–3000 знаков в markdown), `skills[]`
(`{id, name, title, description}`), `connectorCodes[]`, `agentType`, `sortOrder`, `enabled`.
Сортировать по `sortOrder`. Иконок у пресетов в API нет — если дизайну нужны, задавать на клиенте по
`name`.

**Шаг 2 — подтверждение.** Имя (предзаполнено из `title`, редактируется) и инструкция
(предзаполнена из `instructions`). Показывать её целиком нельзя — это пугает; спрятать совсем тоже
плохо — человек должен видеть, что агент настраиваем.

Отдельного «создать из пресета» на бэкенде нет, приложение собирает запрос само:

```
POST <origin>/control/manage/agents/
{ "name": "Домашний бухгалтер",
  "description": "…",
  "instructions": "<возможно отредактированный текст пресета>",
  "type": "<agentType пресета>",
  "skillIds": ["<id каждого элемента preset.skills>"],
  "presetName": "<preset.name>" }
```

`presetName` нужен для аналитики воронки, но проверяется: неизвестное значение — 400.

Ответ содержит поле `fullKey` — это программный ключ агента. **Мессенджеру он не нужен, не
показывать и не хранить.**

**Шаг 3 — открыть коннекторы навыков (без интерфейса).** `skillIds` в создании только привязывает
навыки; доступ к коннекторам они не дают. Навык, у которого хоть один объявленный коннектор не
открыт агенту, сервер считает **неудовлетворённым и не отдаёт агенту вовсе** — ни тулов, ни текста
навыка. Без этого шага получается агент-пустышка: роль выбрана, а ведёт он себя как агент без роли.
Поэтому на каждый код из `preset.connectorCodes` (это объединение коннекторов по навыкам пресета):

```
POST <origin>/control/manage/agents/<agentId>/connections/
{ "connectorCode": "<код из preset.connectorCodes>" }
```

Внутренний коннектор открывается **по коду**, а не по `connectionId`: инстанс у него один на
пользователя, и до первой привязки id у него ещё нет — сервер подставляет его сам. Вызов
идемпотентен. Политики доступа не нужны: модель default-allow, при наличии привязки тул разрешён.

Создание, таким образом, это несколько запросов подряд, и обрыв на любом из них оставляет агента
созданным. Повтор не должен заводить второго: id созданного агента запоминается, и кнопка
продолжает с того шага, где упало.

Кнопка завершения ведёт **сразу в чат**, а не обратно в список: создать переписку
(`POST /manage/webchat/sessions`) и открыть её. Первый экран нового чата должен подсказывать, с чего
начать разговор именно с этой ролью.

## 8. Экраны

1. **Вход** — логотип, строка обещания, форма «почта и пароль», под ней кнопки провайдеров. Рядом
   две двери, упирающиеся в письмо: «забыли пароль» и регистрация; на установке без почты их нет
   вовсе. Форма стоит выше провайдеров намеренно: провайдеры быстрее, но форма — единственный путь
   туда, где провайдер отвязан или его аккаунт на другом ящике.
2. **Ожидание одобрения** — для роли `GUEST`.
3. **Контакты** — главный экран: список агентов, поиск, кнопка создания всегда доступна. Пустое
   состояние работает как онбординг: объясняет, зачем заводить агента, и ведёт к созданию.
4. **Создание агента** — галерея ролей и подтверждение.
5. **Переписки агента** — если у агента их несколько.
6. **Чат** — сообщения, потоковый ответ, вложения, кнопка остановки, подгрузка истории вверх.
   Незаконченное сообщение переживает уход с экрана: текст и вложения хранятся по переписке и
   ждут возвращения. В списках такая переписка помечена словом «черновик» — но наверх не всплывает:
   порядок серверный, и между страницами его не восстановить.
   Картинка из ленты открывается на весь экран: щипок, перетаскивание, двойной тап; выход по
   «назад», крестику и тапу. Просмотр — слой поверх чата, а не маршрут навигации: подписанный
   адрес живёт 15 минут и в back stack протухает.
7. **Профиль и устройства** — кто вошёл, список сессий, выход.
8. **Способы входа** — провайдеры и пароль одним списком, привязка ещё одного, смена пароля.
   Открыт и роли `GUEST`.
9. **Файлы** — свои файлы списком: открыть, сохранить, поделиться, удалить. Из профиля — все, из
   переписки — её вложения; со скрепки тот же экран выбирает, что приложить, и фильтра там нет.

Состояния, которые надо показать явно: ждём одобрения · пустой список агентов · пустой чат ·
загрузка · ошибка отправки с повтором · обрыв WebSocket и восстановление · долгий ответ · агент
выключен (`enabled: false`) · упёрлись в лимит загрузок (429).

## 9. Чего в приложении быть не должно

Интеграции и подключения, навыки, политики доступа, выбор модели и ключи, команды агентов, доски
задач, таблицы, биллинг, настройки воркеров. Если кажется, что экран без них неполон — значит,
экран не про то.

## 10. Чек-лист готовности

- [ ] Вход через Custom Tabs, не через WebView
- [ ] PKCE S256: verifier 43–128 символов, challenge ровно 43
- [ ] `redirectUri` при обмене совпадает с `redirect_to` при старте
- [ ] App Link настроен, `assetlinks.json` опубликован, отпечаток совпадает с рабочей подписью
- [ ] Уход редиректа в браузер не вешает приложение
- [ ] Токены в Keystore, авто-бэкап выключен
- [ ] Обновление токенов однопоточное; `409` — повтор, `403` — вход заново
- [ ] Сетевая ошибка при обновлении → повтор **тем же** токеном в пределах минуты
- [ ] Срок access-токена берётся из `expiresIn`; обновление заранее есть, не только по 401
- [ ] Вход по паролю шлёт `client: "NATIVE"` явно, а не полагается на значение по умолчанию
- [ ] Пароль проверяется по байтам UTF-8, а не по символам
- [ ] `503` на письмах прячет регистрацию и «забыли пароль»
- [ ] Deep link различает `code` (вход) и `link_proof` (привязка)
- [ ] Доказательство привязки гасится сразу по возвращении; четыре `outcome` и 403 обработаны
- [ ] Последний способ входа не предлагается отвязать
- [ ] Роль `GUEST` ведёт на экран ожидания, а не в пустой список
- [ ] Дедупликация сообщений по `messageId`, схлопывание своего эха
- [ ] Отметка прочтения шлёт `id` строки, а не `messageId`
- [ ] Листинг переписок фильтруется `connectorCode=webchat`, иначе в список попадут мессенджеры
- [ ] Кнопка «стоп» отменяет **сессию**, а не запуск
- [ ] Относительный `url` файла собирается как `<origin>/control` + `url`, абсолютный берётся как есть
- [ ] `403` на содержимом лечится перезапросом ссылки, а не сообщением о доступе
- [ ] Загрузка идёт в `/manage/files`, ключ ответа — `id`, ключ в `parts` — `fileId`
- [ ] Загрузка вложения переживает уход с экрана; черновик хранит `agf_`, а не локальный файл
- [ ] Черновик шифруется и уходит вместе с токенами при выходе
- [ ] Слэши в конце путей соблюдены
