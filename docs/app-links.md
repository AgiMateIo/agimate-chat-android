# App Link: что нужно от инфраструктуры

Приложение умеет принимать возврат из браузера двумя способами.

| Адрес | Когда работает | Чем плох |
|---|---|---|
| `agimate://auth` | всегда, сразу | схему может зарегистрировать на себя чужое приложение |
| `https://www.agimate.io/app/auth` | после публикации `assetlinks.json` | требует работы на домене |

Сейчас по умолчанию используется схема — она работает без внешних зависимостей, но безопасной её
считать нельзя. PKCE защищает поток, который начало **настоящее** приложение: без verifier'а
перехваченный код бесполезен. Он не даёт ничего в потоке, который начал **атакующий**: challenge
пришёл в его ссылке, verifier у него, и код, уехавший по схеме в его приложение, обменивается
штатно. Поэтому схема — временный вариант, и App Link заменяет её, а не дополняет.

Сверка адреса на сервере (`app.oauth.native-redirect-urls`) идёт **точным равенством** — ни лишнего
слэша, ни query-параметров в `redirect_to` быть не должно. Схема разрешена там временно: сервер
перестанет её принимать, и копия приложения, не обновившаяся к этому моменту, потеряет вход совсем.
Отсюда порядок: сначала домен, потом релиз со ссылкой, потом время на обновление, и только потом
сервер закрывает схему.

## 1. Опубликовать файл

По адресу `https://www.agimate.io/.well-known/assetlinks.json`, отдавать с
`Content-Type: application/json`, без редиректов и без авторизации.

```json
[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "ru.agimate.mobile",
      "sha256_cert_fingerprints": [
        "96:B0:C5:72:5C:92:CD:C1:D9:F8:78:32:C4:57:B6:49:96:0D:A4:C0:F5:1C:09:55:D0:0F:C5:DC:97:98:DA:D1"
      ]
    }
  }
]
```

Отпечаток выше — **отладочной** подписи с машины разработчика: он годится, чтобы проверить механику,
и не годится для релиза.

## 2. Добавить отпечаток рабочей подписи

`sha256_cert_fingerprints` — массив, в нём может быть несколько значений; отладочный можно оставить
рядом с релизным на время разработки.

Отпечаток своей подписи берётся так:

```
keytool -list -v -keystore <release.keystore> -alias <alias> | grep SHA256
```

**При переходе на подпись Google Play отпечаток меняется.** Play пересобирает и переподписывает APK
своим ключом, и в `assetlinks.json` должен попасть отпечаток из Play Console → *Setup → App
integrity → App signing key certificate*. Если этого не сделать, ссылка молча перестанет открывать
приложение: ошибки не будет, редирект просто уйдёт в браузер.

## 3. Отдать страницу по адресу возврата

`https://www.agimate.io/app/auth` должен отвечать страницей — именно по этому пути, без редиректа на
локализованный (`/ru/app/auth` не подходит: intent-filter приложения заявляет один точный путь, а
человеку с непрошедшей проверкой браузер покажет то, что лежит по исходному адресу).

Сейчас там 307 на `/ru/app/auth`, а `/.well-known/assetlinks.json` отвечает 404 — до того, как оба
пункта закроются, включать флаг нельзя.

## 4. Включить в приложении

В `app/build.gradle.kts` у флейвора `prod`:

```kotlin
buildConfigField("boolean", "USE_APP_LINK", "true")
```

`dev` остаётся на схеме: ссылка с проверкой домена на эмуляторный хост невозможна, а локальный вход
должен продолжать работать.

## 5. Проверить

```
adb shell pm verify-app-links --re-verify ru.agimate.mobile
adb shell pm get-app-links ru.agimate.mobile
```

У домена `www.agimate.io` должен быть статус `verified`. Затем — живой вход целиком: возврат обязан
попасть в приложение, а не в браузер.

## Чего делать не надо

Пытаться «починить» непрошедшую проверку тем, что приложение начнёт ждать код бесконечно. Проверка
домена может не сработать и по причинам на стороне пользователя — он отключил открытие ссылок в
приложении. Тогда редирект уходит в браузер, кода приложение не видит, и оно обязано это пережить:
экран входа с возможностью повторить. Это уже реализовано (`MainViewModel.onAppResumed`).
